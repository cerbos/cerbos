type:breaking
Query planner emits a `has` operator for presence tests on unknown attributes unless it guards an expression on the same attribute
The most common use of `has()` is as a guard for an expression on the same attribute, as in `has(R.attr.owner) && R.attr.owner == P.id`. The query planner continues to leave such guards out of the plan, so plans for these policies are unchanged. Previously, the planner also replaced every other `has()` on an attribute missing from the plan request with `true`. A condition such as `has(R.attr.owner)` produced a `KIND_ALWAYS_ALLOWED` plan even though `CheckResources` denies resources without `owner`, and a `DENY` rule such as `!has(R.attr.owner)` was dropped from the plan entirely. The planner now emits `{"operator": "has", "operands": [{"variable": "request.resource.attr.owner"}]}` for these presence tests. Query plan adapters that don't handle the `has` operator will reject plans containing it.
