type:breaking
Query planner emits a `has` operator for presence tests on unknown attributes unless it guards an expression on the same attribute
The most common use of `has()` is as a guard for an expression on the same attribute, as in `has(R.attr.owner) && R.attr.owner == P.id`. Most databases do not have or need a special existence check for columns so the query planner ignores such guards. That behaviour remains unchanged.
Previously, the planner also replaced every `has()` on an attribute missing from the plan request with `true`. A condition such as `has(R.attr.owner)` produced a `KIND_ALWAYS_ALLOWED` plan even though `CheckResources` denies requests without the `owner` attribute. A `DENY` rule such as `!has(R.attr.owner)` was dropped from the plan entirely. If the plan simplifies down to a single `has` check, the planner now emits it unchanged to maintain symmetry between check and plan APIs (e.g. `{"operator": "has", "operands": [{"variable": "request.resource.attr.owner"}]}`). This is a potential breaking change because query plan handlers that do not handle the `has` operator would fail after this change.
